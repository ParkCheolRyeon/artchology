01

요청한 피라미드 구조

사용자가 설명한 DDD를 도메인별 최소 루트 + 기능별 자식 + 반복 상세·이력으로 해석했습니다. 부모는 도메인의 정체성을 유지하고 자식은 기능별 데이터를 담당합니다.

  • 루트는 ID, 소유 범위, 생명주기에 필요한 상태만 가집니다. 이메일·목표·본문·결제 정보는 자식에 둡니다.
  • 자식이 부모 FK를 소유합니다. 부모는 자식 ID나 자식 유무 플래그를 갖지 않습니다. 1:1 확장 자식은 부모 ID를 PK/FK로 공유합니다.
  • 자식이 없을 수 있으므로 조회는 필요 기능만 LEFT JOIN합니다. 필수 화면 생성 시 루트와 필수 프로필을 한 트랜잭션으로 생성합니다.
  • 학생–사례, 학생–회기처럼 도메인이 만나는 부분은 연결 테이블을 둡니다. 전체 관계를 억지로 하나의 트리로 만들지 않습니다.
  • 기능을 제거할 때는 자식의 후손·참조·보존할 기록을 먼저 처리합니다. 루트 변경 없이 확장할 수 있다는 뜻이지 FK를 무시하고 즉시 DROP할 수 있다는 뜻은 아닙니다.
02

현재 저장 상태

실제 진입점은 main.tsx → weetory/Shell.tsx입니다. model.ts의 업무 자료는 store.ts의 Zustand 메모리에서만 유지됩니다. auth.ts의 PIN/복구 해시·초기 프로필은 localStorage, 잠금 만료 시각은 sessionStorage에 있습니다.

src/main/data/store.ts에는 이전 모델용 lowdb JSON 저장이 있지만 현재 위토리 화면과 자동 연결되지 않습니다. 기존 관계형 테이블·마이그레이션은 확인되지 않았으며 아래 테이블은 모두 신규 설계안입니다.

03

서버와 기기의 경계

배치 가정: 계정·구독·원격 동의는 서버가 처리하고, PIN·기기 설정·백업 실행은 로컬에 둡니다. 나머지 업무 영역은 하나의 관계형 저장 경계에서 실행하는 논리 모델입니다. 상담 원본을 서버와 로컬 중 어디에 둘지는 아직 확정하지 않았습니다.

ERD의 실제 FK 제안은 각 배치 안에서만 유효합니다. 업무 DB를 로컬에 둘 경우 workspace_member.account_id와 구독·원격 동의 연계는 API 식별자/로컬 미러로 바꾸고 동기화 outbox·충돌 정책을 추가해야 합니다. 이 문서는 분산 저장이 이미 해결됐다고 가정하지 않습니다.

local_device.installation_key와 서버 device.installation_key는 같은 설치를 식별하는 논리 연결이며 DB 간 FK가 아닙니다. 로그인 전 로컬 온보딩 자료는 계정 연결 시 workspace와 매핑합니다. PIN 검증 성공을 서버 계정 인증으로 인정하지 않습니다.

03

무결성과 조회 규칙

  • 타입은 DB 독립 논리 타입입니다. uuid, text, integer, boolean, date, time, timestamp, json을 사용하며 timestamp는 UTC 저장을 전제합니다. 실제 PostgreSQL/SQLite 매핑은 구현 시 결정합니다.
  • 모든 PK는 UUID, created_at은 필수입니다. NULL 표기가 없으면 NOT NULL. UK는 단일 UNIQUE, 복합 UNIQUE와 업무 CHECK는 테이블 상세에 있습니다.
  • 부모 1 → 단일 확장 0..1, 부모 1 → 목록 0..N입니다. 핵심 프로필을 생성 시 필수로 만드는 규칙은 애플리케이션 트랜잭션으로 보장합니다. nullable FK는 대상 0..1입니다.
  • 기본 삭제는 RESTRICT입니다. 소유 자식의 CASCADE는 해당 aggregate 영구 삭제 시에만 허용합니다. 계정→공간, 양식→발송 문서처럼 보존 경계가 다른 자료는 연쇄 삭제하지 않습니다.
  • workspace 범위는 루트에서 유도하며 자식마다 중복 복사하지 않습니다. 연결 테이블의 양쪽 공간/학교 일치는 서비스 트랜잭션과 DB 트리거로 검증합니다. FK만으로 테넌트 일치가 보장되는 것은 아닙니다.
  • 모든 FK에 인덱스. 주요 목록은 school+상태, student+학년도, 일정 기간, delivery.token_hash, account_identity(provider,subject) 중심으로 인덱스를 설계합니다. 부모 조인을 포함하는 유일성은 상세 규칙에 따라 트리거 또는 제약 가능한 번호 할당 구조로 구현해야 합니다.
  • 통계·오늘의 상담·최근 기록·장기 미접촉은 조회 결과이며 별도 정본 테이블을 만들지 않습니다. activeSchoolId, 화면 탭, 검색어, 모달, 토스트도 업무 테이블에서 제외합니다.
  • 읽기 전용 화면 모델은 JOIN/VIEW로 합성합니다. 도메인 원본을 거대한 JSON 컬럼 하나로 숨기지 않습니다. json은 PIN KDF 파라미터처럼 구조가 가변인 기술 설정에만 사용합니다.

01

적용·이관·롤백

  1. 저장 위치·계정 소유권·보존 정책을 확정합니다. 이 문서는 설계 산출물이며 DB나 앱 저장 코드를 변경하지 않았습니다.
  2. 계정/설치/공간 루트, 프로필과 멤버십부터 생성합니다. 같은 배치 안에서 FK 대상 순서로 생성하고 순환 참조는 만들지 않습니다.
  3. 학교·학생 → 사례·번호 → 일정·기록 → 양식·문서·발송·응답 → 작품·기록물 순으로 기능 단위 연결합니다. 로컬 PIN은 별도 마이그레이션 경계로 관리합니다.
  4. Zustand는 UI 상태와 조회 캐시로 유지하고 저장은 repository/service 경유로 옮깁니다. 저장 성공 후 캐시 갱신, 실패 시 토스트와 재시도를 제공합니다.
  5. 기존 lowdb JSON을 백업한 뒤 별도 임포터로 학생·상담·그림을 매핑합니다. 현재 메모리 시연 데이터는 사용자 실자료로 자동 이관하지 않습니다. 로컬 PIN 프로토타입 해시는 운영 전환 시 재등록 정책을 정합니다.
  6. 로그인 만료·재실행 복원·학교 간 격리·중복 코드 사용·동의서 재발송·동시 번호 발급·백업 복원을 검증합니다.
  7. 롤백은 이전 앱/읽기 경로와 백업을 보존하고 신규 쓰기를 중단한 뒤 복원합니다. 운영 자료가 쌓인 자식 테이블은 즉시 DROP하지 않고 내보내기·참조 제거·읽기 전환 후 폐기합니다.
